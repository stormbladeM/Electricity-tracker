# Migrations

`0001_init.sql` is the initial schema for the Nigeria Electricity Tracker: the geographic hierarchy (`states` → `lgas` → `areas`), `discos`, `profiles`, the event-sourced `power_logs`, the derived `outage_intervals` table, `fault_reports`, `fault_confirmations` and the append-only `admin_audit_log` — plus enum types, indexes for the dashboard aggregations, the `auth.users` → `profiles` provisioning trigger, and row level security on every table. The design reference is [`docs/project-plan.md` section 3](../../docs/project-plan.md) for the column set and section 4 for the features that read and write it; the locked-in decisions it encodes (store events not durations, anonymous auth, users read aggregates but only write their own rows) live in [`CLAUDE.md`](../../CLAUDE.md). Migrations are applied in filename order and are written to be safely re-runnable, so add new changes as a new numbered file rather than editing one that has already been applied.

`0002_revoke_trigger_function_execute.sql` closes direct `/rpc/` execution on the three trigger-only functions from `0001`. It revokes from `anon`/`authenticated` by name rather than from `PUBLIC`, because Supabase's default privileges grant EXECUTE to those roles directly. The four query-helper functions stay callable on purpose — they only read the caller's own `auth.uid()`.

`0003_outage_interval_derivation.sql` is the M2 interval derivation job. It adds `public.derive_outage_intervals()`, which rebuilds `outage_intervals` from `power_logs`: per area, a run of consecutive same-status logs collapses to its first log, each `off` opens an interval, the next `on` closes it with `duration_minutes`, and a trailing `off` stays open. Flagged logs are excluded, since `is_flagged` is moderator-only and suspect logs must not skew public uptime. It is re-runnable and incremental — it upserts on the `(area_id, started_at)` unique constraint instead of truncating, and prunes only intervals that no longer derive from any log. The function is `SECURITY DEFINER` (nothing else may write `outage_intervals`), EXECUTE is granted to `service_role` alone, and a `pg_cron` job named `derive-outage-intervals` runs it every 5 minutes; the schedule is unscheduled-then-scheduled so re-running the file cannot stack duplicate jobs.

One numbering caveat: the remote history records that last file as `0004_outage_interval_derivation`. A follow-up to `0002` was applied remotely as `0003_revoke_trigger_function_execute_direct` but folded back into the `0002` file here, so the remote's `0003` slot was already taken. Filename order is what governs a replay from scratch; the remote labels are only a log of what was applied when.
