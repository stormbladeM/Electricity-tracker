# Migrations

`0001_init.sql` is the initial schema for the Nigeria Electricity Tracker: the geographic hierarchy (`states` → `lgas` → `areas`), `discos`, `profiles`, the event-sourced `power_logs`, the derived `outage_intervals` table, `fault_reports`, `fault_confirmations` and the append-only `admin_audit_log` — plus enum types, indexes for the dashboard aggregations, the `auth.users` → `profiles` provisioning trigger, and row level security on every table. The design reference is [`docs/project-plan.md` section 3](../../docs/project-plan.md) for the column set and section 4 for the features that read and write it; the locked-in decisions it encodes (store events not durations, anonymous auth, users read aggregates but only write their own rows) live in [`CLAUDE.md`](../../CLAUDE.md). Migrations are applied in filename order and are written to be safely re-runnable, so add new changes as a new numbered file rather than editing one that has already been applied.

`0002_revoke_trigger_function_execute.sql` closes direct `/rpc/` execution on the three trigger-only functions from `0001`. It revokes from `anon`/`authenticated` by name rather than from `PUBLIC`, because Supabase's default privileges grant EXECUTE to those roles directly. The four query-helper functions stay callable on purpose — they only read the caller's own `auth.uid()`.

`0003_outage_interval_derivation.sql` is the M2 interval derivation job. It adds `public.derive_outage_intervals()`, which rebuilds `outage_intervals` from `power_logs`: per area, a run of consecutive same-status logs collapses to its first log, each `off` opens an interval, the next `on` closes it with `duration_minutes`, and a trailing `off` stays open. Flagged logs are excluded, since `is_flagged` is moderator-only and suspect logs must not skew public uptime. It is re-runnable and incremental — it upserts on the `(area_id, started_at)` unique constraint instead of truncating, and prunes only intervals that no longer derive from any log. The function is `SECURITY DEFINER` (nothing else may write `outage_intervals`), EXECUTE is granted to `service_role` alone, and a `pg_cron` job named `derive-outage-intervals` runs it every 5 minutes; the schedule is unscheduled-then-scheduled so re-running the file cannot stack duplicate jobs.

`0004_lga_uptime_ranking.sql` is the M4 aggregate behind the area dashboard's comparison chart and national ranking. It adds `public.lga_uptime_ranking(p_days integer)`, which rolls up, over the last `p_days` days: per-area off-minutes (from `outage_intervals`, clipped to the window) and log/contributor counts (from `power_logs`, flagged excluded), then per-LGA a log-count-weighted mean of area uptime plus summed outage/log counts and a distinct contributor count. Only LGAs with evidence in the window are returned, ordered by uptime. It is a plain `stable` function (not `SECURITY DEFINER`) reading only already-public tables, so it runs under the caller's RLS; EXECUTE is granted to `anon` and `authenticated` because the comparison and ranking show on pages that need no login.

`0005_fault_confirmation_counts.sql` is the M5 confirmation flow. `0001` created `fault_reports.confirm_count` as "a cached counter maintained by the M5 confirmation flow"; this is that maintenance. It adds `public.sync_fault_confirm_count()`, a `SECURITY DEFINER` trigger function fired `after insert or delete` on `fault_confirmations`: it recomputes `confirm_count` for the affected fault and, if the fresh count reaches 3 while the fault is still `reported`, advances it to `confirmed`. That is the only status transition the flow performs — everything past `confirmed` is moderator/admin work — and status never moves backward, so removing a confirmation cannot demote a fault. It has to be a trigger because `0001`'s RLS lets a client only *insert* its own `fault_confirmations` row; `confirm_count` and `status` are not client-writable. EXECUTE is revoked from `anon`/`authenticated` (trigger firing does not check it), same as the `0002` trigger functions.

`0006_fault_photo_storage.sql` creates the `fault-photos` Storage bucket that `fault_reports.photo_url` points into, plus RLS on `storage.objects`: public `select` (fault photos show on no-login pages, like the reports themselves), `insert` only under the caller's own `<auth.uid()>/…` path for a non-banned user, and `delete` of one's own objects (so replacing a photo on a still-untriaged report works). The bucket is `public` with a 5 MiB / image-mime backstop; the client downscales to a small JPEG before uploading.

`0007_admin_metrics.sql` is the M6 admin overview's data layer: `public.admin_overview_stats(p_days)` (one row of headline numbers — log/contributor/user/fault volumes, the open moderation and triage backlogs, median fault resolution time, and a log-weighted national uptime that reuses `lga_uptime_ranking` rather than re-deriving the window arithmetic) and `public.admin_growth_series(p_days)` (per-day logs, distinct contributors, new accounts and new faults, bucketed by `Africa/Lagos` calendar day, with explicit zero rows for quiet days). Both are `SECURITY DEFINER` and open with an `is_moderator_or_admin()` check that raises `insufficient_privilege` — chosen over caller RLS because `profiles` is owner-and-moderator readable, so a plain function would hand a regular user quietly wrong totals instead of a refusal. EXECUTE is granted to `authenticated` only.

`0008_log_moderation.sql` is the M6 moderation queue, end to end. `0001` created `power_logs.is_flagged`/`flag_reason` and said moderation owned them; nothing ever set them, so the queue would have opened empty. This adds: `reviewed_at`/`reviewed_by` on `power_logs` (a *decision*, without which the detector and the moderator fight — a cleared flag would be re-raised fifteen minutes later); `public.flag_suspect_power_logs()`, a `SECURITY DEFINER` detector on a 15-minute `pg_cron` job that raises four heuristics in priority order (future timestamp, rapid toggling under 3 minutes, more than 10 logs in an hour, and a log contradicted by three or more other contributors in the area with none agreeing), skipping reviewed logs and idempotent on re-run; `public.review_power_logs(uuid[], boolean, text)`, which applies a keep/reject decision *and* writes one `admin_audit_log` row per log in the same transaction, so an action cannot land unrecorded; `public.set_user_moderation(...)` for ban/unban, trust score and notes, admin-only because `0001`'s `profiles_guard_privileged_columns` trigger already refuses those edits from anyone else; and the two queue reads `public.admin_flagged_logs(integer)` and `public.admin_contributors(integer, boolean)`, which are functions rather than PostgREST selects because `power_logs.user_id` references `auth.users`, not `profiles`, so there is no foreign key for an embed to travel along. Rejecting never deletes: a flagged log is already skipped by `derive_outage_intervals` and `lga_uptime_ranking`, so the evidence stays and only the influence goes.

One numbering caveat: the remote history records `0003_outage_interval_derivation` as `0004_outage_interval_derivation` and `0004_lga_uptime_ranking` as `0005_lga_uptime_ranking`. A follow-up to `0002` was applied remotely as `0003_revoke_trigger_function_execute_direct` but folded back into the `0002` file here, so every later file sits one slot ahead remotely — `0005_fault_confirmation_counts`, `0006_fault_photo_storage`, `0007_admin_metrics` and `0008_log_moderation` land as `0006`, `0007`, `0008` and `0009`. Filename order is what governs a replay from scratch; the remote labels are only a log of what was applied when.
